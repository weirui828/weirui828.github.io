Deep dives: evaluation

Two projects where the real work was measuring things honestly. Read the summary, or open the full write-up.

human-loop · research project · Python, scikit-learn, DistilBERT

A benchmark score of 0.998 that meant nothing

Can a model trained on clean, synthetic support data decide which real customer messages need a human? I trained a simple baseline and a fine-tuned DistilBERT on a synthetic dataset, then tested both on real tweets to customer support.

On synthetic data both models scored about 0.998 macro F1. On real tweets they dropped to 0.58 and 0.56. Better labels helped far more than a better model.

Read the deep dive

The setup

  • Training data: Bitext, a synthetic customer-support dataset. Its 27 intents were mapped to a yes/no question: does this need a human? That gave 17,770 self-service and 6,865 escalated examples (72% / 28%), so I report macro F1 and ROC-AUC, not accuracy.
  • Real-world test: 5,000 threads from Twitter customer support (TWCS), labeled with an LLM, using only the customer's first message, which is all a live system has.
  • Models: TF-IDF with logistic regression as the baseline, and a fine-tuned DistilBERT. Both reuse the same 80/20 splits, checked by re-scoring the saved baseline before comparing anything.

What the numbers showed

  • The synthetic benchmark can't tell the models apart. DistilBERT beats the baseline by 0.0005 there, a handful of rows out of 4,927.
  • Trained on synthetic data, the transformer is worse on real tweets (0.5568 vs 0.5816). It became over-confident: almost every tweet scored near zero, so at the usual 0.5 cut-off it flagged almost nothing. Its best cut-off was 0.01, and it still lost.
  • Real labels are worth more than a better model. Retraining on real labels added 0.15 macro F1 for the baseline and 0.24 for DistilBERT. Switching to DistilBERT on real data added only 0.06.
  • The gain from DistilBERT is precision, not recall. It raises far fewer false alarms but misses slightly more escalations. Macro F1 likes that trade; a support desk might not, so the cut-off has to be chosen on purpose.

Where it failed, and why

The average hides which kinds of message survive the move. Recall on real tweets, for the baseline trained on synthetic data:

In red: the two categories explained below.

The worst failures were not noisy language. They came from the labels. The synthetic data files password resets and invoice lookups as self-service. On Twitter, a lockout or a double charge is exactly what needs a person. The model read the words correctly and applied the wrong rule, and the two things a support desk can least afford to misroute are locked-out users and missing money.

What it costs

Neither number blocks anything at this scale. The bigger point: a frontier LLM takes about a second or more per message and bills per token every time. Distilling its judgment into a small model means paying the frontier price once, during labeling, instead of on every ticket.

TriageKit · open-source tool · Python, TypeScript, SQLite

Evaluation rules built into the product

A local, human-in-the-loop classifier that decides which customer messages need a person. The interesting part is not the model. It is the rules that keep the evaluation honest, enforced by the tool instead of left to discipline.

The threshold is chosen on validation data only, the test set is scored once, and a model that misses the contract's limits cannot be promoted.

Read the deep dive

Three-way routing instead of yes or no

Every message gets a score. Below a low threshold it is handled automatically, at or above high it is escalated, and anything in between goes to a person to review.

A label contract defines “needs a human”

Each dataset comes with a YAML contract: the two classes with examples and rules for unclear cases, the allowed categories, how the threshold is chosen, and the limits for automatic routing, such as the maximum auto-error rate and the maximum number of missed positives.

Rules the tool enforces

  • Snapshots are immutable. Every training run uses a fixed copy of the data, so a result can always be traced back.
  • The threshold and routing band are chosen on validation data only. The test set is scored once, after the policy is fixed.
  • No policy within the contract's limits, no promotion. A run that can't meet them stays a run.
  • Runs are compared only on identical data under the same contract.
  • Feedback becomes new labels, but feedback on validation or test rows is kept for audit only and never used for training.
  • Promotion and rollback are explicit and logged, and every decision records the model version that made it.

Watching it after launch

A monitor page tracks volume, the mix of actions, the review rate, the override rate and score drift against the production model. A scripted demo scores a message, records a correction, retrains, and shows that the training data changed while the evaluation data stayed fixed.
